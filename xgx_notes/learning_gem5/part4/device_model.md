# MMIO / DMA：从教学对象到加速器设备

> 本章是开发任务书，仓库尚未因本文新增该设备。先完成 Part 2 的事件与端口练习。

## 参考入口

阅读 `src/dev/io_device.hh`、`io_device.cc`、`dma_device.hh`、`dma_device.cc` 与 `src/dev/Device.py`，理解 PIO 与 DMA 的职责。继承现有基类前核对其端口、地址范围和回调约定。

## 先定义接口

下表是练习建议，不是 gem5 内置寄存器协议。实现前确定寄存器宽度、对齐、端序、允许的访问长度与错误行为。

| 寄存器 | 建议宽度 | 语义 |
|---|---|---|
| SRC / DST | 64 bit | DMA 源/目的物理地址 |
| LEN | 64 bit | 字节长度 |
| START | 32 bit | 空闲时写入提交任务 |
| STATUS | 32 bit | idle / busy / done / error |

状态流：idle → read → compute → write → done；错误进入 error，并定义清除方式。忙时重复 START 不能悄悄覆盖正在执行的任务。

## 分三步实现

1. **PIO + 固定延迟**：解析寄存器，START 后调度事件，延迟后完成；验证地址范围和非法访问。
2. **单请求 DMA 拷贝**：读入缓冲再写回，所有写响应完成后置 done；处理零长度、越界与不对齐的明确策略。
3. **分块与有限并发**：区分排队、已接受、已完成请求；记录 outstanding 上限、读写字节和任务时延。

提交者可以先用仿真侧测试驱动。SE 用户程序必须有明确设备地址映射；真实驱动与中断路径另行使用 FS 验证。

## 异步事务必须回答的问题

- `sendTimingReq()` 返回 false 后谁保存 Packet？谁等 retry？
- 请求被接受后，响应返回前哪些缓冲与上下文必须存活？
- 上游暂时不能接受响应时，谁保存响应并等待重试？
- 多笔请求如何匹配各自任务、偏移与完成计数？
- 何时可以释放缓冲、报告完成或接受下一任务？

可画“请求已发出/被拒绝/等待响应/响应受阻”状态图。严格遵守所用端口和基类的所有权约定，不能用周期性重发代替 retry 协议。

## 正确性与可见性

非一致性 DMA 不自动保证 CPU Cache 中脏数据对设备可见。初期可以选择无 Cache 或明确的不可缓存映射；随后验证所选软件/模型中的 cache maintenance 与内存屏障。具体策略需与 CPU、ISA、内存系统一致。

至少验证：小块/跨块拷贝、连续任务、忙时提交、错误参数、请求背压、响应背压及最终输出。对于已接受且需要响应的事务，排空后接受数与完成数必须匹配。未验证 checkpoint/drain 前，不宣称设备支持检查点恢复。

## 验收产物

提交寄存器规范、状态机、C++/Python/SConscript 变更、独立配置、正确性记录和带宽曲线。固定延迟设备是协议验证工具，不能代表真实 NPU 性能。

## 分步实验 D：每一步只增加一种能力

**重点逻辑：提交只是接受任务，完成必须意味着所有输出已可见；控制面负责描述任务，数据面负责实际搬运。** 以下文件名与寄存器布局为建议，需要自行实现。

### D1：先完成接口规范

建议地址偏移为 SRC=0x00、DST=0x08、LEN=0x10、START=0x18、STATUS=0x1c。PIO 基地址选在普通 RAM 范围之外，并在配置中验证没有重叠。明确零长度、地址溢出、不支持的宽度、busy 时 START 的处理方式。

交付一张寄存器表和状态图；只有接口规则确定，才能写测试的预期结果。

### D2：固定延迟完成，不做 DMA

建议新增 `LearningDma.py`、`learning_dma.hh/.cc` 和 SConscript 注册；选择 PIO/设备基类前读其 read/write 和延迟返回约定。实现空闲时 START 把参数快照保存，置 busy，调度完成事件；忙时参数写入不能改变已接受任务。

测试驱动先由 gem5 模型发 PIO 事务，不引入 OS。完成事件置 done；驱动读 STATUS 并验证。测试零延迟与正延迟、重复 START 和非法偏移。记录“提交接受时间”到“完成时间”，区分 PIO 传输耗时与处理延迟。

**通过条件**：一项任务只接受一次、完成一次；参数与错误行为符合规范。

### D3：单块拷贝

连接 DMA 请求端到互联请求侧，读取确定性的源数据，再将相同数据写入目的地址。先使用无 Cache 系统、互不重叠的源和目的，长度取 64B。以已有 DMA 基类的完成回调语义为准，所有读写缓冲保持存活到相应访问结束。

驱动在开始前填充源与目的哨兵，done 后逐字节检查目的、源未被破坏以及边界外哨兵。可以用 functional 访问初始化/检查内存，但 ROI 中实际搬运必须走 timing 路径。

**通过条件**：数据正确、写回完成后才 done；此时再测 1B、63B、65B 等边界。若实现尚不支持非对齐，应返回定义好的错误，不能静默错误完成。

### D4：分块与并发

先固定 block=64B、outstanding=1，再增到 2/4。每块保存任务 ID、偏移、阶段与缓冲；最后一块用真实剩余长度，不能越界填满一个整块。

记录已提交块数、读完成数、写完成数、在途峰值。完成条件应同时覆盖：没有未发工作、没有等待响应、所有目标写入完成。若 DmaPort 内部会拆分请求，区分设备块计数与底层 Packet 计数。

**预期**：并发增加可能掩盖延迟，但受内存带宽限制后趋于饱和；如果不变，检查是否仍然逐块等待写完才发下一块。

### D5：背压和可见性

使用可控测试端点拒绝一次请求，再拒绝一次响应，核对包保留、retry 和完成计数。最后才加 CPU Cache，并实现选定的可见性方案；比较源被 CPU 修改后 DMA 是否能读到新值。

**最终交付**：D1～D5 各一条运行记录与失败样例解释。只有确认数据路径正确，才把拷贝替换成 NPU 计算。
