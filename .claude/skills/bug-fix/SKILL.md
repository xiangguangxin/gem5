# 有证据的 Debug

目标是解释“哪个条件触发了哪处契约违背，如何导致症状”，并提供复现、定位与修复前后的证据。按问题规模使用流程；信息不足时报告假设和下一步，不声称百分之百确定。

## 1. 建立基线

先看起始 diff，保留用户改动。记录预期/实际行为、准确命令与退出码、版本/二进制、输入、配置、种子及频率。优先缩小复现；偶发问题保留失败样本和成功对照，不要求每次必现才允许调查。缺少复现时可继续静态分析或增加定向观测，避免猜测式改代码。

区分阶段：加载前失败、配置/构建失败、运行崩溃、结果错误、进度停滞。动态库未找到先查环境；结果错误先查预期与首次数据偏离；卡死先查等待关系，不能都从崩溃栈入手。

## 2. 分类但不抢先定责

读取 [根因象限与证据](references/root-cause.md)。按需求、设计、实现、配置/环境四象限核对根因来源；文档、需求预期或测试本身也可能错误。给各象限假设标注待验证/支持/排除；证据不足时保持 unknown，不硬塞象限。允许主因、促成因素、检测缺口并存。

## 3. 找到首次偏离

- 先读现有日志与错误前文，用事务/地址/对象 ID、仿真 tick 和队列串联路径，区分根因事件与后续连锁报错。
- 从错误值的使用点向生产、修改与交接处回溯，找最后正确值和第一个错误值。跨模块在输入/输出边界检查契约。
- C/C++ 崩溃、对象寿命、异常或卡死需要运行时证据时，按 [日志与 GDB 定位](references/logs-gdb.md) 操作；纯配置问题无需机械启动 GDB。
- 每轮选择能区分候选原因的最小实验，写清假设、预期观察、实际观察和结论。优先一次改变一个条件；调试器、额外日志也可能改变竞态。

## 4. 修复与验证

修复要对应已证实的因果链。设计问题先修订契约和受影响设计，再同步代码/测试；改变用户关键设计选择时按现有授权执行。实现问题核对同类调用方、所有权、边界和时序。不要通过删除断言、吞错误、放宽期望或任意增加延时隐藏故障。

尽可能用同一输入证明修复前失败、修复后通过，新增能区分正确/错误行为的回归用例。先跑相关测试，再按影响范围扩展；不无条件要求整个 gem5 全量回归。非确定问题报告样本数、种子与仍存的不确定性，“未再出现”不等于证明根治。工具不可用时明确未验证项，不自动安装。

## 5. 交付与沉淀

简要交付：症状/影响 → 根因分类与置信度 → 因果链及来源行号/日志/栈 → 修复 → 验证命令/退出码 → 剩余风险。未定位时给出已排除项和下一项可区分实验。

有可复用结论时衔接 [project-memory](../project-memory/SKILL.md)：保存必要的脱敏证据收据，经验先 candidate，经语义审查再 accepted。测试通过本身不自动证明根因；不把原始 core dump、完整日志或秘密写入长期记忆。不因调试自动提交、推送或启动额外 Agent。
